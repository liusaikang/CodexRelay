# 持久化定时任务

HTTP 模式启动后，控制台的“定时任务”页可创建周期规则。填写名称、每轮任务内容和间隔分钟数，可选填系统提示词；创建后默认启用，首次触发时间为创建时刻加一个间隔。规则列表分别展示任务内容和系统提示词；未填写时显示使用默认提示词。可查看执行轮次、暂停或启用规则，也可手动触发一轮。暂停只阻止新的定时触发，已经在等待的轮次仍会执行。

每条规则固定 **4 个工作位**，每个位复用自己的 Codex 原生会话。同一个位上的轮次串行，不同位可并行；因此控制台是一条规则，底层最多有 4 条独立的会话历史，并非让同一原生会话并发执行。第 5 轮起保存在该规则的等待队列，任一工作位的任务结束后自动提交最早的等待轮次。其他规则各有自己的 4 个工作位，但所有任务仍共享全局 `maxConcurrent`、`maxQueued` 和模型额度。如果全局并发小于 4，单条规则也达不到 4 个同时运行；生产基础值已设为 4，控制台保存的运行配置仍会覆盖该基础值。

规则和轮次分别保存在 `dataDir/schedules/definitions/`、`dataDir/schedules/runs/` 的 JSON 文件中，不依赖进程内缓存。非空 `systemPrompt` 随轮次保存并传给任务；省略、`null`、空串或全空格时不保存覆盖值，在该轮实际开始执行时读取默认提示词文件。已有规则和轮次无需迁移。同一工作位的后续轮次也可使用不同系统提示词。每轮使用稳定幂等键；重启后恢复等待轮次和已接收任务的关联，不重复提交。意外中断的运行任务由核心任务服务标记为 `interrupted`，不会自动重放该轮；下一轮可能继续使用同一工作位会话，业务侧应保证外部操作幂等。停机跨过多个周期时只补记最近的一个到期轮次，避免启动瞬间无限补跑。

规则等待容量为 1000 轮。手动触发超过上限时返回 429；自动触发达到上限时记录一条失败轮次 `SCHEDULE_BACKLOG_FULL`，便于运维发现，不会无限增加待执行任务。定时层等待不受核心任务的 `queueTimeoutSeconds` 影响；只有提交到核心任务队列后才开始计算该期限。

定时规则的任务内容、历史结果和会话同样可能包含敏感信息，只允许已登录的控制台访问管理接口。控制台接口不接受服务 Bearer Token 单独管理规则。规则定义一经创建，任务内容不可编辑；修改内容时应暂停旧规则并创建新规则，以便保留既有执行记录。删除需在控制台二次确认，并删除规则定义与该规则的全部执行轮次文件，包括等待中的轮次；已有普通任务及其结果仍保留。有已提交且未完成的轮次时拒绝删除，等待其完成后重试。当前版本仅支持按固定分钟间隔触发，不支持 Cron 表达式，也不负责业务数据领取/回写的去重；这些应由任务所用的 Skill 或外部脚本保证。

接口由登录控制台使用，写请求还要求同源 `Origin`：

| 接口 | 用途 |
| --- | --- |
| `GET /console/schedules` | 列出规则及运行/等待数量 |
| `POST /console/schedules` | 创建规则，字段为 `name`、`question`、`intervalMinutes`、`enabled`，可选 `sandboxMode`、`systemPrompt`（UTF-8 最多 16 KiB） |
| `DELETE /console/schedules/{id}` | 删除规则定义与执行轮次；有已提交轮次时返回 409 |
| `GET /console/schedules/{id}/runs` | 查看该规则的执行轮次 |
| `PUT /console/schedules/{id}/enabled` | 传入 `{ "enabled": false }` 暂停或启用 |
| `POST /console/schedules/{id}/run` | 手动触发一轮 |

修改部署配置或升级时先停止服务，保留 `dataDir` 和 `codex.home`。定时规则数据的读写与任务数据使用同一个单实例锁，不要让多个进程同时操作同一目录。
